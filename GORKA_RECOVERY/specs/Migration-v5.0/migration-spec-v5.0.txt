Backend Auth Strategy
typescript
// src/backend/middleware/auth.ts
export const authenticateToken = async (req: Request, res: Response, next: NextFunction) => {
  try {
    let token = null;
    
    // 1. Check Authorization header (Bearer token) — for desktop app
    const authHeader = req.headers.authorization;
    if (authHeader && authHeader.startsWith('Bearer ')) {
      token = authHeader.split(' ')[1];
      console.log('[AUTH] Token from Authorization header (desktop)');
    }
    
    // 2. Check cookie — for web browsers
    if (!token && req.cookies) {
      token = req.cookies.gorka_session;
      console.log('[AUTH] Token from cookie (web)');
    }
    
    if (!token) {
      return res.status(401).json({ success: false, error: 'No token provided' });
    }

    const decoded = jwt.verify(token, process.env.JWT_SECRET || 'default-secret');
    (req as any).user = decoded;
    return next();
  } catch (error) {
    return res.status(403).json({ success: false, error: 'Invalid or expired token' });
  }
};

};

// Authenticated fetch with Bearer token
const authFetch = async (url: string, options: RequestInit = {}): Promise<Response> => {
  const token = await getToken();
  return fetch(url, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { 'Authorization': `Bearer ${token}` } : {}),
      ...(options.headers || {}),
    },
  });
};

Good — every item from the last round got a real fix, not a cosmetic one: local server now requires a shared secret, CORS is restricted to actual app origins, and the Bearer-token strategy correctly separates desktop auth from browser cookie auth. This is close to genuinely ready. A few things left, roughly in order of how much they matter:
1. JWT_SECRET || 'default-secret' is back — this exact bug was caught and fixed months ago in your marketing-site spec, and it's resurfaced here in the new shared auth middleware.
typescript
const decoded = jwt.verify(token, process.env.JWT_SECRET || 'default-secret');
If JWT_SECRET is ever unset in production, every token silently gets verified against a public, guessable string instead of failing loudly. This is the copy-paste hazard of iterating across many documents — worth a global search for default-secret across your whole codebase before this ships, since it's clearly capable of reappearing.
2. getLocalSecret() writes the shared secret to a plaintext file (local-secret.txt) via writeTextFile. It solves problem #1 from last round (an unauthenticated local server) but the secret protecting it isn't itself protected — any other process or user account on the same machine can simply read that file and impersonate the desktop app to its own local API. For a product whose entire premise is "protect regulated debtor data," this is worth tightening: store it via the OS keychain (same mechanism already correctly chosen for the auth token — @tauri-apps/plugin-store or safeStorage) rather than a bare text file in the app data directory.
3. LOCAL_SECRET is compared with !== — not constant-time. Minor in this specific context (attacker would need local code execution to time the comparison at all, at which point they could likely just read the file per #2), but worth using crypto.timingSafeEqual() for the comparison as a matter of habit, especially since this codebase already imports crypto in that same file.
4. The local server binds to a fixed, guessable port 31415, but nothing prevents port squatting. If any other local process (malicious or just a port conflict) is already listening on 31415 before your app starts, app.listen(PORT) will either throw or silently fail depending on how errors are handled — neither path is addressed here. Worth adding an explicit .on('error', ...) handler that tries a fallback port or surfaces a clear "port unavailable" message to the user, rather than the app failing mysteriously.
5. authenticateLocal middleware is applied via app.use('/api/local', authenticateLocal) — confirm this line's position relative to the CORS middleware and route definitions actually guards every route beneath it, since Express middleware order matters and this file interleaves CORS setup, secret loading (which is awaited at module scope — a top-level await, which needs your build/runtime to actually support that syntax; worth confirming Tauri's bundler doesn't choke on it), and route registration in a way that's easy to accidentally reorder during future edits.
6. Role naming is now internally consistent — "Supervisor" is explicitly listed as the legacy name for "Client Admin" in the table, which resolves the collision flagged twice before. Good, this one's actually closed.
7. Minor: /api/search, /api/reports, /api/exports are still in the forbidden list without qualification — good, that's actually cleaner than the earlier conditional wording ("if it can search debtor names"). This one's also resolved from before.
Net: this is a coherent, implementable spec, and most of the hard architectural questions (data boundary, desktop vs. browser, auth split, CORS) are genuinely settled now. Items 1 and 2 are the two I'd actually block on — both are real gaps in the exact thing this document exists to guarantee (debtor data protection), and both have concrete, already-modeled fixes elsewhere in your own spec (the auth-token secure-storage pattern) that just need to be applied consistently to the local secret too.
